# Компоненты PGVal

| Каталог | Состояние к КТ‑1 |
|---|---|
| [app/](app/) | Стенд Kafka/Flink, запуск авторской SST, скрипты проверок с перезапуском TaskManager, каркас командного задания |
| [executor/](executor/) | Python-прототип управления Java-процессом, отказ по барьеру, журнал и сверка с эталоном демо |
| [generator/](generator/) | Генерация самодостаточного плана v2 для SST |
| [validator/](validator/) | Независимый Oracle для SST и проверка сохранённых журналов |

Следующий шаг — выполнить один общий [план v2](PLAN.md) на SST и передать фактические журналы валидатору. Затем команда подключит новую топологию и новый отказ.

## Генератор и независимый валидатор

Генератор и валидатор запускаются как одноразовые сервисы в [общем Docker Compose](compose.yaml) из одного образа. Генератор сохраняет единый план с событиями, а валидатор анализирует переданные ему журналы. [Генератор в Docker](generator/README.md) · [Валидатор в Docker](validator/README.md)

Для локальной разработки нужен Python 3.12 без внешних зависимостей. Команды выполняются из корня репозитория.

```bash
python3 -m unittest discover -v
python3 -m pgval.generator --list-generators
python3 -m pgval.generator --generator sst-uniform --windows 2 --pages 2 --events-per-window 10 --out-dir runs/sst
```

Генератор модульный: `sst-random` и `sst-uniform` реализуют общий интерфейс в `generator/generators/base.py`, модули регистрируются в `generator/generators/__init__.py`. Генератор совместно развивают разработчики валидатора и исполнителя. Валидатор не импортирует генератор или вычислительный код Flink.

Создаётся один самодостаточный `plan.json` версии 2: параметры, события внутри действий `publish`, темп отправки, условия запуска и действия `fault`. [Формат и семантика плана](PLAN.md), [полный пример](generator/examples/plan.json). Генератор не создаёт журналы фактического исполнения.

`--events-per-window` означает общее число событий окна, а у временного `pgval/app/fakegen` — число на страницу. Baseline поддерживает только `--window-ms 60000`. Генератор добавляет один завершающий элемент для одного раздела Kafka; расширение на несколько разделов требует финализации каждого раздела.

## Контракт журналов

| Файл | Содержимое и назначение |
|---|---|
| `plan.json` | Конфигурация, `actions` с полными событиями и отказами, граница `evaluate_until_ms` |
| `input.tsv` | Необязательный для v2 журнал фактической отправки: JSON-ключ, табуляция, ClickEvent |
| `click.jsonl` | Фактический вход, прочитанный из Kafka; при наличии проверяется совпадение с отправкой с учётом кратностей |
| `output.jsonl` | PageStatistics из `output`, прочитанные с `read_committed`: `page`, `windowStart`, `windowEnd`, `clickIds`, `updateIds` |
| `lateOutput.jsonl` | Поздние события; текущая монотонная нагрузка ожидает пустой поток |
| `validation.json` | Статус, правильность, потери, повторы и подробности расхождений |
| `timeline.txt`, `stand.log` | Диагностика запуска и воздействий; текущий чекер их не использует для доказательства выполнения отказа |

Чекер принимает JSON-массивы, JSONL и TSV входа; границы окон — epoch milliseconds или строки ISO из юнит-тестов. Порядок выходных записей и ID внутри результата несущественен, кратности существенны. Между разделами Kafka порядок чтения может отличаться: `click.jsonl` сопоставляется с отправкой как мультимножество. Для v2 сравнение выполняется с событиями плана; при наличии `--inputs` также сверяется журнал отправки. При несовпадении входов возвращается `invalid_input`, до выяснения доставки правильность приложения не оценивается.

Oracle рассчитывает ожидаемые результаты по событиям плана v2; для архивного v1 используется отдельный входной файл. Он поддерживает SST с уникальными ID и монотонным временем входа; поздние и намеренно повторно опубликованные события требуют расширения семантики. Эталон вычисляется по входу, границы измерения не выводятся из выхода приложения. Повторы окончательных результатов учитываются отдельно для A1/E1. Скрытые внутренние повторы, удалённые агрегатором Flink, по этому выходу не обнаружить.

## Проверка сохранённого запуска Flink

```bash
python3 -m pgval.validator \
  --plan pgval/validator/examples/sst-archive-plan.json \
  --inputs pgval/app/checks/sst-gen/results/20261103T155921/input.tsv \
  --outputs pgval/app/checks/sst-gen/results/20261103T155921/output.jsonl \
  --late-outputs pgval/app/checks/sst-gen/results/20261103T155921/lateOutput.jsonl \
  --complete --report /tmp/pgval-validation.json
```

Результат: 60 ожидаемых и 60 правильных окон, 0 пропусков/повторов. Сохранён в `validator/examples/sst-archive-validation.json`. В этом архиве есть только журнал отправки, фактический вход Kafka отдельно не сохранён.

Журналы `pgval/app/checks/sst-gen/results/20261103T155921/` уже находились в командном
репозитории в коммите `71b4364` до добавления `pgval`. Для проверки валидатора
они прочитаны без изменений. Файл `validator/examples/sst-archive-plan.json`
подготовлен для повторного анализа этого архива по параметрам нагрузки;
`sst-archive-validation.json` и `sst-archive-docker-validation.json` — результаты
нашего чекера, а не новые журналы исполнения Flink. Приложение и отказы в этой
проверке не запускались. Прототипы `pgval` запускаются отдельно от стенда.

`--complete` означает подтверждение завершения сбора вызывающей стороной. Без него статус `incomplete`. Плановое развитие исполнителя — явное подтверждение watermark/commit и завершения сбора. Временные метрики требуют offset/partition и временных меток, которых текущие значения JSONL не содержат.

Контейнерный запуск описан в [validator/README.md](validator/README.md).
