# pgval/app/: тестируемая система

Ответственный: Ван Петр.

Цепочка Kafka → Flink → Kafka, на которой проводятся эксперименты. По умолчанию на ней работает задание SST автора (`jawadtahir/DSPF-BM@d74c9b80a3a1`, собрано из исходников без изменений) — это baseline. С `JOB=own` запускается собственное задание команды из [job/](job/); собственная топология в нём ещё не реализована.

```
генератор → Kafka "click" → задание Flink (окна 60 с по странице) → Kafka "output" → валидатор
                                                                  └→ Kafka "lateOutput" (опоздавшие события)
```

Генератору, валидатору и исполнителю отказов не нужно знать про Flink: достаточно писать в Kafka и читать из неё.

> **Временные компоненты.** [fakegen/gen.py](fakegen/gen.py) и сравнение результата в [checks/](checks/) написаны только для того, чтобы проверить, что стенд работает. Это не генератор и не валидатор проекта: их делают другие участники команды, и эти заглушки будут заменены. Сравнение идёт по окнам, без подсчёта надёжности по отдельным событиям, как в статье.

## Запуск

Нужны Docker с Compose v2, Python 3 и репозиторий автора на закреплённой ревизии:

```bash
git clone https://github.com/jawadtahir/DSPF-BM ~/repos/DSPF-BM
git -C ~/repos/DSPF-BM checkout d74c9b80a3a1
```

```bash
pgval/app/baseline/build.sh                              # сборка задания автора (один раз, ~4 мин)
docker compose -f pgval/app/compose.yaml up -d --wait    # стенд + задание SST; PG=a1 для at-least-once
pgval/app/checks/sst-small/run.sh                        # малый пример с известным ответом
pgval/app/checks/sst-gen/run.sh                          # временный генератор + сравнение
docker compose -f pgval/app/compose.yaml down -v         # остановка
```

Веб-интерфейс Flink: <http://localhost:8081>. Каждый сценарий проверки начинает с чистого стенда.

Сбой в сценарии `sst-gen`: `PG=a1 KILL_AFTER=12 DOWN_FOR=5 pgval/app/checks/sst-gen/run.sh --events-per-window 500 --windows 10 --rate 1000` (TaskManager останавливается через 12 с и запускается через 5 с).

## Конфигурации и версии

| | `compose.yaml` | `compose.multi.yaml` (`STAND=multi`) | У автора |
|---|---|---|---|
| Брокеры Kafka, разделы × реплики | 1, 1 × 1 | 3, 3 × 3 | 3, 3 × 3 |
| TaskManager, параллелизм | 1, 1 | 3, 3 | 3, 3 |
| Память стенда (измерено) | ~1,3 ГБ | ~3,5 ГБ | JM 10 ГБ, TM 15 ГБ каждый |
| Веб-интерфейс Flink | `:8081` | `:8082` | |

Контрольные точки (5 с, EXACTLY_ONCE), heartbeat (1 с / 3 с), стратегия перезапуска и тайм-аут транзакции (30 с) — как у автора. Контрольные точки хранятся в томе Docker вместо HDFS.

Версии: Flink и коннектор Kafka 1.17.1, как в коде автора; брокер Kafka 3.7.0 (у автора 3.6.0 из Bitnami; официальный образ Apache — с 3.7.0); JDK 11. Переход на Flink 2.x требует изменения кода автора и отложен.

## Интерфейс

**Вход `click`:** ключ — страница (строка JSON), значение:

```
{"id":1,"timestamp":"2026-11-03T10:00:05.000","page":"/help"}
```

`id` уникален; `timestamp` в UTC и **монотонно возрастает**. **Других полей быть не должно:** лишнее поле приводит к бесконечному перезапуску задания (проверено).

**Выход `output`:** одна запись на страницу и окно

```
{"page":"/help","windowStart":1793700000000,"windowEnd":1793700060000,"clickIds":[1,3,5],"updateIds":[]}
```

- окна по 60 с, без перекрытия, `[начало, конец)`; время в миллисекундах;
- порядок `clickIds` не определён — сравнивать как множество;
- **читать только с `read_committed`**, иначе в E1 видны отменённые результаты.

**`lateOutput`:** по записи на каждое опоздавшее событие.

Окно выдаётся, когда событие с более поздним временем продвигает водяной знак за конец окна; в E1 — ещё и после следующей контрольной точки (до 5 с).

## Что выяснилось

- **В compose-файлах автора E1 не включается:** `-pg ¼{PG}` (U+00BC вместо `$`), задание работает в A1. Мы передаём режим явно.
- **Dockerfile автора не собирается** без отсутствующего `settings.xml` и доступа к GitHub Packages; `baseline/build.sh` собирает модуль `datamodel` из исходников.
- **Водяной знак обновляется раз в 200 мс**, поэтому опоздание события зависит от момента поступления, а не только от входа.
- **Настройки контрольных точек читает клиент, отправляющий задание.** Без них задание работает, но не делает контрольных точек, и результаты E1 не фиксируются — без ошибок.

## Результаты проверок

| Проверка | Режим, сбой | Потеряно / повторено / неверно (окон) |
|---|---|---|
| Малый пример, генератор (один узел и несколько) | E1, без сбоя | 0 / 0 / 0 |
| Остановка TaskManager на 5 и 39 с (один узел и несколько) | E1 | 0 / 0 / 0 |
| Остановка брокера на 10 с (несколько узлов) | E1 | 0 / 0 / 0 |
| Остановка TaskManager на 5 с (один узел; несколько — 1 из 3 запусков) | A1 | 0 / **6** / 0 |

В A1 повторяются окна, выданные между последней контрольной точкой и сбоем, поэтому результат зависит от момента сбоя. Подробности — в [КТ1](../../nis/checkpoints/01.md); данные каждого запуска — в `checks/*/results/`.

## Ограничения

- Всё работает на одном компьютере; абсолютные пропускная способность и задержка со статьёй не сравниваются.
- Большинство вариантов запущено по одному разу.
- Сбои вводятся вручную в сценарии проверки; управляемый ввод отказов — задача исполнителя.
