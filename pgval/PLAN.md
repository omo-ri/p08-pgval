# План теста, версия 2

`plan.json` — единственный входной файл описания теста. Он содержит конфигурацию
вычислений, все события и действия, включая запланированные отказы. Готового
ожидаемого результата в нём нет: его вычисляет независимый Oracle.
[Полный небольшой пример](generator/examples/plan.json).

## Действия

`actions` — список объектов с уникальными `id`, типом `type` и условием `trigger`.
Позиция в списке не означает ожидания завершения предыдущего действия.
Публикации последовательны, воздействия могут выполняться параллельно с ними.
Ссылки на действия должны вести к ранее объявленным ID, что исключает циклы.

`publish` содержит `topic`, положительный `rate_per_second` (событий/с реального
времени) и массив `events`. Каждое событие содержит ровно `id`, `timestamp`, `page`.
Kafka-ключ определяется `input.key_field`. Первая публикация запускается по
`test_start`, следующая — после завершения предыдущей публикации. Завершение
публикации означает получение подтверждений записи всего её набора в Kafka.
Ожидаемая последовательность событий — объединение `events` публикаций в порядке
списка. Event time внутри событий не задаёт реальную задержку отправки.

`fault` содержит `scenario`, `target`, положительный `duration_ms` и необязательный
объект `parameters`. Конкретное значение `scenario` и параметры согласует исполнитель.
Длительность отсчитывается от фактического введения воздействия; завершение действия
означает снятие воздействия и окончание предусмотренной сценарием процедуры.
Неизвестный исполнителю сценарий должен завершать запуск ошибкой, а не пропускаться.
В примере используется обычный перезапуск процесса; новый отказ проекта не выбран.

## Условия запуска

- `{"type":"test_start","delay_ms":0}` — от начала теста, после готовности стенда.
- `{"type":"action","action_id":"publish-main","phase":"started","delay_ms":100}` — через 100 мс после начала указанного действия. `phase` также может быть `completed`.
- `{"type":"signal","name":"window_closed","timeout_ms":5000,"delay_ms":0}` — после первого подходящего сигнала с момента начала теста. Исполнитель подписывается до начала подачи. `timeout_ms` ограничивает ожидание сигнала от начала теста; если сигнал не пришёл, сценарий не выполнен. Точный контракт сигнала задают разработчик приложения и исполнитель.

Отсутствующий `delay_ms` равен нулю. Ожидание по времени выражается через него.
Сигнал или запись действия в плане не являются доказательством фактического отказа.

## Генерация и выполнение

Генератор создаёт `publish-main`, затем добавляет переданные через `--faults-json`
действия воздействий и `publish-tail` для продвижения watermark. Файл `--faults-json`
нужен лишь при построении плана: его содержимое полностью копируется внутрь,
при выполнении никаких ссылок на этот файл нет. Без этого параметра создаётся
план обычного режима. Все параметры нагрузки и гарантии также записаны в план.

Поле `completion` задаёт требование финализации: продвижение watermark всех разделов
и фиксация выхода, а также завершение всех воздействий и восстановительных действий. Это обязанность исполнителя, не автоматический результат
отправки последнего события. Текущая генерация хвоста поддерживает один раздел.

Исполнитель должен прочитать план, выполнить публикации и воздействия, сохранить
фактический вход `click.jsonl`, `output.jsonl`, `lateOutput.jsonl` и журнал действий.
Каждая запись журнала действий должна ссылаться на `action_id` и содержать фазу,
время, исход и сведения об ошибке/наблюдении воздействия. Реализация исполнителя
данного формата остаётся отдельной задачей участника «Исполнитель». Управление процессом,
подтверждение SIGKILL и связывание записи воздействия с action_id проверены в
[локальном прототипе](executor/README.md). Генератор и валидатор работают с файлами плана
и журналов.

## Валидация

Для v2 достаточно `--plan` и журналов выхода: `--inputs` необязателен и означает
дополнительную сверку журнала отправки с планом. `--observed-inputs` сверяет
фактический вход Kafka с запланированными публикациями по значениям и кратностям,
без предположения общего порядка чтения разных разделов. При расхождении возвращается
`invalid_input`: сначала необходимо выяснить доставку, оценка приложения не подменяется
проверкой другого входа. Без этих журналов проверяется только соответствие выхода плану.

Oracle считает SST независимо от генератора и приложения. Общий `pgval/plan.py`
определяет только структуру плана и извлечение событий; вычислений Flink в нём нет.
Текущий Oracle требует уникальные ID и монотонное event time. Повторные публикации,
удаление событий из подачи и поздние события потребуют отдельного расширения семантики;
сетевой повтор пакета не означает автоматического повтора бизнес-события.

При наличии `fault` отчёт содержит `fault_execution: "not_checked"`: статус `pass`
относится только к выходу, не к успешности введения сбоя. Без `--complete` результат
остаётся `incomplete`. Старые планы v1 и архивные журналы поддерживаются с обязательным
`--inputs`; новые планы генератор записывает исключительно в версии 2.
