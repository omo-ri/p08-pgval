# Описание проекта

## Назначенное задание

P08. PGVal: сквозная проверка гарантий потоковой обработки. Карточка: `project-tasks/p08-pgval.md` в репозитории курса (копия: [requirements/task-p08-pgval.md](../requirements/task-p08-pgval.md)). Статья: J. Tahir и др., «How Reliable Are Streams? End-to-End Processing-Guarantee Validation and Performance Benchmarking of Stream Processing Systems», PVLDB 2024.

## Выбранный технический путь

Сочетание авторского артефакта и самостоятельной реализации:

- **Потоковая система — Apache Flink** с Kafka на входе и выходе. Из трёх систем артефакта (Flink, Kafka Streams, Storm) выбрана одна, как требует карточка.
- **Baseline — задание SST автора** (`App.java` из `jawadtahir/DSPF-BM@d74c9b80a3a1`), собранное из исходного кода без изменений и запущенное на нашем стенде. Новая топология сравнивается с ним на том же стенде.
- **Стенд собран заново для одного компьютера.** Скрипты автора рассчитаны на Docker Swarm из нескольких виртуальных машин с жёстко заданными адресами и путями, поэтому они не используются. Конфигурация Kafka и Flink перенесена из файлов автора; отличия перечислены в [app/README.md](../app/README.md#конфигурации-и-версии).
- **Новая оконная топология, независимый эталон и новый отказ реализуются самостоятельно.**

Версии: Flink 1.17.1 и коннектор Kafka 1.17.1, как в коде автора (в статье указан Flink 1.18.0); брокер Kafka 3.7.0 (у автора 3.6.0 из образа Bitnami, официальный образ Apache доступен начиная с 3.7.0); JDK 11.

### Данные и проверка правильности

Генератор и независимый валидатор пока являются прототипами для SST baseline. Проверены юнит-тесты, контейнерный запуск и анализ сохранённых результатов; сквозное выполнение плана v2 ещё не подключено к исполнителю.

Генератор разрабатывают совместно участники «Генератор / Валидатор» и «Исполнитель». Генератор модульный: доступны `sst-random` и `sst-uniform`. Общий формат плана и интерфейс модулей позволяют выбирать способ формирования событий через параметры запуска; описания отказов встраиваются в тот же план. Модули задают данные и действия, а исполнитель выполняет полученный план. Новые модули подключаются без изменения валидатора, если сохраняются контракт данных и семантика вычислений.

Генератор создаёт один [plan.json версии 2](../pgval/PLAN.md): настройки, события внутри действий `publish`, темп отправки и действия `fault` с условиями запуска. Исполнитель выполняет план и сохраняет фактические журналы. Генератор и валидатор запускаются отдельными одноразовыми сервисами [Docker Compose](../pgval/compose.yaml) из общего образа.

Валидатор работает независимо от приложения: извлекает ожидаемый вход из плана, рассчитывает эталон собственным Oracle и сравнивает его с выходом Flink. При наличии журналов отправки или фактического входа Kafka сначала проверяется их совпадение с планом; расхождение даёт `invalid_input`. Вычислительные функции приложения не используются. Для новой топологии добавляется отдельная реализация Oracle с явно заданной семантикой. Состояние прототипов описано в [КТ1](checkpoints/01.md#генератор-и-независимый-валидатор).

Ниже перечислены ожидаемые результаты к концу проекта; текущий объём прототипов указан отдельно в КТ1.

| Результат | Как проверить |
|---|---|
| Модульный генератор событий и планов, общий для двух участников | Одинаковые параметры, seed и описания отказов дают побайтово одинаковый план; версия генератора и параметры записаны внутри. Для серии экспериментов сохраняется SHA-256 плана. Проверяются уникальность ID и границы окон |
| План теста как список действий, совместно с участником «Исполнитель» | План задаёт публикации событий и воздействия с идентификаторами и условиями запуска; исполнитель сохраняет фактические исходы. В прототипе реализован самодостаточный план v2 с событиями, действиями publish/fault и условиями запуска; исполнение действий интегрирует участник «Исполнитель» |
| Независимый Oracle для SST baseline и новой топологии | Эталон вычисляется по событиям плана независимо от кода приложения; фактический вход сверяется с запланированным; сам Oracle проверяется на маленьких входах с вручную рассчитанными ответами |
| Валидатор результатов | По ключу, окну и кратностям входных ID обнаруживаются потери, повторы и неверные результаты. Проверяется случай, когда потеря одного события компенсирована повтором другого и число событий совпало |
| Раздельная оценка правильности и гарантии A1/E1 | В E1 повторный эффект считается нарушением; в A1 идентичные повторные окончательные результаты допустимы, но повторы остаются в отчёте. Законное участие события в нескольких окнах и обновления результатов учитываются согласно выбранной новой топологии |
| Адаптер к интерфейсу приложения | Принимаются сохранённый фактический вход и JSONL-выход `output`/`lateOutput`, полученный с `read_committed`; числовые границы окон нормализуются. Проверяется отдельно от вычисления Oracle |
| Машинный отчёт и данные для анализа | Отчёт содержит пропуски, лишние вклады, неправильные результаты и долю правильных окон. Совместно с исполнителем собираются временные отметки для throughput, задержки и восстановления |

Oracle не использует готовый ручной ответ при экспериментальном запуске: ручной `expected` нужен только его юнит-тестам. Гарантия движка проверяется отдельно от полного совпадения ответа; сохранённое в `lateOutput` событие не считается автоматически учтённым в основном агрегате. Подтверждение факта отказа предоставляет исполнитель. При наличии действий `fault` текущий валидатор указывает `fault_execution=not_checked`: `pass` относится к результату обработки. Текущий Oracle поддерживает SST с уникальными ID и монотонным event time; повторные публикации и поздние события требуют расширения семантики.

## Поддерживаемые сценарии

### Уже проверено на baseline (SST)

- **Обычный режим.** Поток событий нажатий на 6 страниц, 60-секундные окна. Ожидание: каждое окно выдано ровно один раз со всеми идентификаторами событий. Проверено в E1 на одном и нескольких узлах.
- **Перезапуск процесса.** Один TaskManager принудительно останавливается (`docker kill`) и через 5–40 с запускается снова. Ожидание: в E1 нет потерь и повторов; в A1 возможны повторы окон, выданных после последней контрольной точки. Проверено: в E1 — ни потерь, ни повторов; в A1 — 6 повторов окон в части запусков.
- **Отказ брокера Kafka** (только на стенде с тремя брокерами). Один брокер останавливается на 10 с. Проверено в E1: потерь и повторов нет.

### Планируется

- **Сетевая задержка** между компонентами, как в сценарии автора (задержка 500 мс при тайм-ауте heartbeat 3 с).
- **Новая топология.** Выбирается командой. Кандидаты:
  - *скользящие окна* — окна перекрываются, одно событие попадает в несколько окон;
  - *окна с допустимым опозданием* — одно окно выдаётся несколько раз, по обновлению на каждое опоздавшее событие;
  - *сеансовые окна* — окно по активности пользователя, окна сливаются; во входе нужен идентификатор пользователя;
  - *двухуровневые окна* — второе окно агрегирует результаты первого, например два задания, связанные через топик Kafka.
- **Новый отказ, привязанный к этапу обработки.** Сценарий, условие срабатывания и способ подтверждения воздействия определяет участник «Исполнитель» совместно с разработчиком приложения. Генератор представляет этот сценарий в плане, валидатор использует журнал фактического выполнения при анализе результатов.

### Ограничения сценариев

- Одна потоковая система (Flink), один компьютер: до 3 брокеров Kafka и 3 TaskManager в контейнерах.
- Набор отказов будет уточнён вместе с участником «Исполнитель».

## Упрощения

- **Все узлы работают на одном компьютере.** Механизмы репликации, контрольных точек и восстановления работают так же, как в кластере, но пропускная способность и задержка ограничены общими CPU и диском и не сравниваются с абсолютными значениями статьи.
- **Меньше памяти, чем у автора:** JobManager 1 ГБ (у автора 10 ГБ), TaskManager 1–1,5 ГБ (у автора 15 ГБ).
- **Контрольные точки хранятся в общем томе Docker**, а не в HDFS.
- **Пока все запуски выполняются на одном компьютере.** Работают обе конфигурации стенда: один узел и три брокера с тремя разделами и параллелизмом 3 ([КТ1, П6](checkpoints/01.md)). Использовать ли несколько компьютеров, решим после первых результатов.
- **Режим E1 включается явно.** В compose-файлах автора параметр гарантии передаётся с ошибкой (`¼{PG}` вместо `${PG}`), из-за чего задание всегда работает в A1. Поэтому наши результаты E1 нельзя напрямую сравнивать с запусками скриптами автора.
