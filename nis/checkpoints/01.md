## Краткий итог

Проверки приложения П1–П8 приведены ниже. Подготовлены прототипы модульного генератора и независимого валидатора для SST с единым планом v2; 35 тестов прошли. Валидатор читает форматы стенда; на сохранённом запуске Flink подтверждено совпадение всех 60 окон. Следующий шаг — интеграция исполнителя плана v2 и свежий сквозной запуск. ## Технические проверки

Тестируемая система — цепочка Kafka → Flink → Kafka с заданием SST автора (`jawadtahir/DSPF-BM@d74c9b80a3a1`) в качестве baseline — развёрнута на одном компьютере. Описание стенда, версий и отличий от конфигурации автора: [app/README.md](../../app/README.md). Архивные проверки П1–П8 выполнялись с временным генератором и средствами сравнения приложения. Прототипы генератора и валидатора проверяются отдельно; к скриптам стенда они не подключены.

| № | Что проверяли | Команда | Ожидали | Получили | Материалы |
|---|---|---|---|---|---|
| П1 | Задание автора собирается из исходного кода без изменений | `app/baseline/build.sh` | jar задания | `topology.jar` собран | [build.sh](../../app/baseline/build.sh) |
| П2 | Стенд запускается, SST работает в режиме E1 | `docker compose -f app/compose.yaml up -d --wait` | задание `RUNNING`, контрольные точки каждые 5 с | как ожидали | [compose.yaml](../../app/compose.yaml) |
| П3 | Малый пример с известным ответом: 12 событий, граница окна, опоздавшее событие | `app/checks/sst-small/run.sh` | 6 окон и 1 опоздавшее событие, как в ответе | совпадает | [вход и ответ](../../app/checks/sst-small/), [результаты](../../app/checks/sst-small/results/) |
| П4 | Генерированная нагрузка без сбоев, до 30 001 события | `app/checks/sst-gen/run.sh` | нет потерянных, повторённых и неверных окон | совпадает | [результаты](../../app/checks/sst-gen/results/) |

| П6 | Стенд из 3 брокеров, 3 разделов и параллелизма 3; сбои TaskManager и брокера | `STAND=multi app/checks/sst-gen/run.sh …` | как в П4–П5 | E1 — без потерь и повторов; A1 — повторы в одном запуске из трёх | [compose.multi.yaml](../../app/compose.multi.yaml), [результаты](../../app/checks/sst-gen/results/) |
| П7 | Вход с лишним полем | запись в топик `click` | ошибка разбора | задание перезапускается бесконечно и не обрабатывает следующие данные | [интерфейс](../../app/README.md) |

Каркас собственного задания подготовлен заранее, чтобы проверить, что гарантии E1 сохраняются без изменённого коннектора автора. Эталонный конвейер повторяет SST и нужен только для сравнения с baseline; собственная топология — ко второй точке.

Найденная ошибка артефакта: в compose-файлах автора задание запускается с `-pg ¼{PG}` (символ U+00BC вместо `$`), поэтому режим E1 при запуске скриптами автора не включается. Мы передаём режим явно.

### Генератор и независимый валидатор

Прототипы размещены в [pgval](../../pgval/README.md); команды выполняются из корня репозитория. Генератор поддерживает выбор модуля; его дальнейшая разработка и формат плана — совместная задача участников «Генератор / Валидатор» и «Исполнитель». Валидатор использует независимый Oracle и анализирует сохранённые результаты.

| Что проверялось | Команда в локальной копии | Ожидание и результат |
|---|---|---|
| Генератор, Oracle, валидатор и контракт журналов | `python3 -m unittest discover -v` | 35 тестов; 35 OK, повторно проверено при подготовке отчёта |
| Выбор алгоритма генерации | `python3 -m pgval.generator --list-generators` | Два модуля: `sst-random`, `sst-uniform` |
| Известный ответ, границы окна и полнота | Юнит-тесты Oracle с ручным expected | Совпадение; пропуски/неверные окна обнаруживаются |
| Компенсирующие потеря и повтор | Подстановка повторного ID вместо другого при прежнем числе элементов | Обнаруживаются один пропуск и один лишний вклад |
| Режимы A1/E1 | Одинаковый окончательный результат повторён | A1 допускает повтор с диагностикой; E1 отклоняет; потери/неправильный ответ отклоняются в обоих режимах |
| Завершение сбора | Проверка без подтверждения complete | Статус incomplete; пропуск не объявляется окончательным |
| Самодостаточный план v2 и ошибки структуры | `python3 -m unittest pgval.generator.tests.unit.test_action_plan -v` | Создаётся только plan.json; события и отказ встроены; повторные ID действий, неверные ссылки и параметры отклоняются |
| Проверка выхода по плану без отдельного входного файла | `python3 -m unittest pgval.validator.tests.unit.test_logs.ActionPlanValidationTests -v` | Ручной ответ принимается, неверный выход отклоняется; несовпадающий журнал отправки даёт invalid_input; факт отказа отмечен not_checked |

Зафиксированный вывод локальных тестов:

```text
Ran 35 tests in 0.428s
OK
```

Прототипы используют только стандартную библиотеку Python 3.12. Код размещён по компонентам `pgval/generator` и `pgval/validator`, тесты — внутри `tests/unit`. Генератор создаёт [единый план v2](../../pgval/PLAN.md) с событиями внутри `publish` и описаниями `fault`; поддержаны три типа условий запуска. Фактическое исполнение действий остаётся задачей исполнителя. Oracle не вызывает функции приложения. Ручной expected используется в юнит-тестах и малой проверке связи контейнеров; при анализе архива Flink ответ вычисляет Oracle.

Проверены доступные материалы стенда для согласования интерфейса:

- [Контракт приложения](../../app/README.md#интерфейс): вход содержит id/timestamp/page, выход — PageStatistics, чтение read_committed.
- [Реальный выход малого примера](../../app/checks/sst-small/results/20261103T142537/output.jsonl) имеет JSONL-формат и числовые windowStart/windowEnd. [Поздний поток](../../app/checks/sst-small/results/20261103T142537/lateOutput.jsonl) отдельный. Валидатор поддерживает JSONL, TSV входа и числовые границы окон; также сохранена поддержка JSON-массивов юнит-тестов.
- [Результат временного сравнения](../../app/checks/sst-small/results/20261103T142537/compare.txt): 6 основных окон и 1 позднее событие совпали с ожидаемыми. Это результат проверки участника «Приложение», не результат нашего Oracle.
- [Пример запуска с отказом](../../app/checks/sst-gen/results/20261103T155921/): сохранены input.tsv, output.jsonl, lateOutput.jsonl, args.txt и timeline.txt. Они проверены независимым Oracle: 60/60 окон, 0 пропусков и лишних вкладов; [архивный план v1](../../pgval/validator/examples/sst-archive-plan.json), [отчёт](../../pgval/validator/examples/sst-archive-validation.json) и [команда](../../pgval/README.md#проверка-сохранённого-запуска-flink). Журналы уже присутствовали в репозитории в коммите `71b4364`, до добавления `pgval`; они не создавались и не изменялись при проверке валидатора. План для чтения архива и отчёты сравнения подготовлены отдельно. Это повторный анализ через совместимость с v1 и отдельным входным журналом; основной формат прототипов — v2. Свежий стенд не запускался. В архиве нет отдельного журнала входа, прочитанного из Kafka.

Событийные ID и границы окон доступны для проверки правильности. Времён фактической записи/наблюдения в сохранённых значениях JSONL нет: метрики latency/throughput требуют дополнить сборщик метаданными Kafka или отметками одних часов. Timeline позволяет исследовать перезапуск процесса, но не заменяет измерение устойчивого восстановления полезной обработки.

Прототип офлайн-валидатора собран и запущен в Docker через Compose: на архиве Flink получен `pass`, 60/60 правильных окон, без пропусков и лишних вкладов. [Команды и диагностика доступа](../../pgval/validator/README.md#доступ-к-docker), [отчёт контейнера](../../pgval/validator/examples/sst-archive-docker-validation.json). Docker daemon работает; текущему пользователю недоступен сокет, поэтому проверка выполнена через `sudo` с передачей UID/GID для записи отчёта. Контейнер валидатора запускается отдельно и читает сохранённые журналы.

Прототип генератора также собран и запущен как одноразовый контейнер общего образа `pgval:local`. Два запуска `sst-uniform` с одним окном, двумя событиями и описанием перезапуска дали побайтово одинаковый `plan.json` v2 — единственный файл результата генератора. Файл принадлежит пользователю хоста. Контейнер валидатора прочитал события из плана без `--inputs` и подтвердил ручной ответ для одного окна. Отказ не вводился: в отчёте `fault_execution=not_checked`. Это проверка файлового интерфейса, без запуска Flink. [Команды и параметры](../../pgval/generator/README.md).

## Ресурсы

Конфигурации и измеренная память стенда указаны в [app/README.md](../../app/README.md#конфигурации-и-версии): около 1,3 ГБ для одного узла и 3,5 ГБ для нескольких контейнерных узлов.

Для генератора и валидатора доступны Python 3.12.3 и файловая система; малые генераторы и проверки выполнены. Основной способ запуска — Docker Compose; Python на хосте нужен только для локальной разработки и юнит-тестов компонентов `pgval`. Полная серия требует совместного ограничения ресурсов стенда и измерительных процессов, см. [план](../experiment-plan.md#конфигурации-и-план-запусков). Контейнерный запуск валидатора проверен на сохранённых журналах Flink.

## Риски и следующие шаги

Риски части «Генератор / Валидатор»:

| Риск | Действие и ответственный | Срок |
|---|---|---|
| Прототип валидатора проверен на архиве, нужен свежий набор журналов | Разработчик валидатора: согласовать с исполнителем контракт входа и выхода и проверить предоставленные им результаты | До сквозной проверки КТ2 |
| Новая топология меняет кратность и версии результатов | Разработчики приложения и валидатора: выбрать топологию и зафиксировать семантику Oracle | Выбор до сдачи КТ1, реализация к КТ2 |
| План v2 ещё не подключён к исполнителю | Разработчики генератора и исполнителя: интегрировать действия и журнал фактических исходов | До интеграции исполнителя к КТ2 |
| Метаданные для временных метрик не сохраняются | Разработчики генератора и исполнителя: дополнить сборщик; проверить сопоставимость часов | Пробный сбор до основной серии |

Параметры пилота и основной серии — в [плане эксперимента](../experiment-plan.md). Раздел рисков исполнителя дополняется его ответственным.
